# Contract Mutation Testing

Contract mutation testing validates the linter itself by generating small semantic mutations of reviewed contracts and measuring whether the linter detects each change.

## Concept

**Mutation testing** answers: *"Does the linter actually detect violations of the constraints I wrote down?"*

Given a contract, the mutation tester:
1. Generates **mutants**: small, meaningful semantic changes (e.g., flip a requirement to a prohibition, delete a rule, swap action order)
2. Runs the linter on each mutant
3. Classifies results:
   - **KILLED**: The linter detected the change (diagnostics differ from original)
   - **SURVIVED**: The linter missed the change (diagnostics unchanged)
   - **EQUIVALENT_SUSPECTED**: Both original and mutant have no diagnostics; likely equivalent
   - **CRASHED**: The mutant broke the contract structure (reported separately)

**Mutation score** = killed / (total - equivalent - crashed)

A high score indicates sensitive, comprehensive linting rules. Surviving mutants point to vacuous rules or blind spots.

## Usage

Run mutation testing on any contract:

```bash
python -m prompt_skill_linter CONTRACT.json \
  --tools TOOLS.json \
  --runtime RUNTIME.json \
  --mutate
```

### Options

- `--max-mutants N`: Limit to first N mutants (default: unlimited)
- `--operators OP1,OP2`: Include only specific operators (default: all)
- `--format json`: Output JSON instead of human-readable text
- `--output FILE`: Write report to file

### Example

```bash
python -m prompt_skill_linter examples/ordering-auth-violation.contract.json \
  --tools examples/ordering-tools.json \
  --runtime examples/ordering-runtime.json \
  --mutate
```

Output excerpt:
```
Total mutants: 21
Killed: 5
Survived: 13
Equivalent (suspected): 0
Crashed: 3
Mutation score: 23.81%

Surviving mutants (13):
--------------------------------------------------
[workflow_0_ordering_0_swap_before] swap_before_actions
  Swap first/second in before rule auth-before-data
  Location: /workflows/0/ordering_rules/0/actions
  Hint: Mutant survived: swapping actions in before rule did not change diagnostics
```

This reveals that swapping the before-rule actions went undetected, indicating a potential blind spot in the ordering checker for this specific contract structure.

## Mutation Operators

### Rules
- **flip_kind**: Flip requirement ↔ prohibition
- **swap_priority**: Swap priorities of two rules
- **equalize_priority**: Set one rule's priority to match another
- **drop_exception**: Remove an exception from a rule
- **add_trivial_exception**: Add a never-matching exception
- **negate_effect**: Flip Boolean effect value
- **delete_rule**: Remove a rule entirely

### Workflows
- **drop_precondition**: Remove an action precondition
- **drop_effect**: Remove an adds or removes effect
- **delete_action**: Remove an action
- **remove_goal_literal**: Remove a goal literal

### Ordering Rules
- **swap_before_actions**: Swap first/then in a before rule
- **change_exactly_to_at_most**: Change exactly_once → at_most_once
- **drop_ordering_rule**: Delete an ordering rule
- **swap_mutual_exclusion**: Swap actions in mutual_exclusion (should be equivalent)

### Tool Manifest
- **make_required_optional**: Make a required argument optional
- **remove_tool_argument**: Remove an argument entirely

## Interpretation

### High Mutation Score (>80%)
The linter is sensitive to the declared constraints. Most semantic changes are detected.

### Low Mutation Score (<50%)
Many mutations survive, suggesting:
- Vacuous rules (conditions that never match)
- Unchecked properties (e.g., workflow structure not validated)
- Redundant rules (shadowed by higher-priority rules)

### Surviving Mutants
Each surviving mutant is a specific hypothesis: *"Deleting/changing X has no observable effect."* Investigate whether:
- The rule is truly vacuous (intended)
- The linter has a blind spot (should be fixed)
- The contract has redundant declarations

### Crashed Mutants
Mutations that break the contract schema (e.g., deleting a referenced rule) are reported separately. They indicate structural dependencies rather than semantic checking gaps.

## Guarantees and Limitations

- **In-memory only**: No source files or contract JSONs are modified on disk.
- **Deterministic**: Mutant IDs and ordering are stable across runs.
- **Bounded**: Tests only the mutations generated by defined operators, not all possible semantic changes.
- **Kill criterion**: Compares normalized diagnostic sets (code + responsible rules + severity). Other report changes (witnesses, metadata) are ignored.
- **No execution**: Mutations test the linter, not runtime behavior. A killed mutant means the linter detected the change, not that the contract would fail at runtime.

## Self-Mutation: Testing the Tester

The mutation testing implementation includes guard tests that verify its own correctness:

1. **Original-not-modified guard**: Ensures mutations use deep copy and don't alter the input contract
2. **Kill-comparison guard**: Verifies that diagnostic comparison logic correctly identifies changes
3. **Crash-handling guard**: Confirms that crashed mutants are reported separately

The test suite includes deliberate scenarios where disabling each guard causes test failures, proving the guards are active and necessary.
